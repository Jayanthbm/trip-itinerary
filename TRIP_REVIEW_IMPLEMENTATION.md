## 1. Goal

For **archived or completed trips**, let the user:

1. **Review every predicted cost** — after the trip has ended (§13), record the **actual cost** for each planned item (flights, trains, bus, hotels, activities, and every timeline entry that has a cost).
2. **Track completion** — mark each planned timeline item as **done / not done** ("did we visit it or not"), with optional notes.
3. **One-click entry point** — a prominent **"Review" button at the top** of the trip view (and on dashboard cards) to start/continue a review.
4. **Planned vs Actual budget** — the **Budget section** shows what was **planned** next to what was **actually spent**, with variance per item, per section, and grand total.

Everything stays **client-side** (this is an offline PWA — no backend), persisted in IndexedDB with the trip, and included in backup export/import.

## 2. Current Architecture (relevant pieces)

| Area | Where | Notes |
|---|---|---|
| Trip storage | IndexedDB (`getAllTrips`, `saveTrip`, `importTrips`) via `src/App.jsx` | Trips are full JSON objects. `loadRecentTrips()` auto-archives past trips (`isTripInPast` → `archived: true`). |
| Backup | `handleExportBackup` / `handleImportBackup` in `src/App.jsx` | Exports the raw trips array; import validates + re-normalizes each trip. Anything on the trip object that survives `normalizeData` is automatically backed up. |
| Tab system | `src/components/Tabs.jsx` + `ItineraryView.renderContent()` | Top-level tabs: `prebooking`, `days` (`day-N`), `budget`. Content switches on the `activeTab` string. |
| Budget view | `src/components/BudgetView.jsx` | Reads `prebookingData` (flights/trains/bus/rooms/activities) + per-day **active plan** timeline & additionalBudget. Has a local `parseCost()`. Renders planned costs only. |
| Helpers | `src/utils/itineraryHelpers.js` | `isTripInPast`, `getTripCountdown`, `calculateTotalBudget`, `validateData`, `normalizeData`, `getCurrencySymbol`. |
| Trip cards | `src/components/TripCard.jsx` + `DashboardView.jsx` | Already distinguishes `status` (active/archived) and shows countdown/completed badges. |
| Checklist / prebooking status | localStorage keys like `` `${itineraryKey}_prebook_${category}_${id}` `` | ⚠️ Existing pattern stores UI state in **localStorage only** — it is *not* part of the trip, not exported in backups, and keyed by a fragile `title_startDate_endDate` string. |

### Key constraints discovered in code

- **`normalizeData` strips unknown fields** from `prebookingData` items and from `days[].plans[].timeline[]` items (it rebuilds them field-by-field). A top-level `...data` spread **does** survive — so review data must live at the **trip top level**, not inline on timeline items.
- **Prebooking items get `id: i + 1`** regenerated by `normalizeData` — ids are index-based, effectively positional.
- **Timeline items have no ids at all** — review entries must be keyed by position + a label snapshot for drift detection.
- **Budget tab is gated**: `renderContent()` renders BudgetView only when `activeTab === 'budget' && hasPrebooking`. Trips without prebooking data currently can't open the budget tab at all.
- `calculateTotalBudget` counts **only the active plan's** timeline items and excludes `excludeFromBudget === true` activities. The review/actuals must mirror these same rules or planned-vs-actual numbers won't line up.
- `parseCost` is **duplicated** (local copy in `BudgetView.jsx` and inline in `calculateTotalBudget`) — consolidate while touching this area.
- **⚠️ Deeper audit findings:** cost parsing is actually inconsistent in **4 places**, range cost strings (`"₹600 – ₹1,000"`) mis-parse, and `additionalBudget` items keyed by `item` (real sample data) are silently dropped by `normalizeData`. Full details and fixes: **`REVIEW_READINESS_PLAN.md`** — these must be fixed (Phase 0) before review numbers can be trusted.

## 3. Data Model

Add an optional top-level `review` object to the trip. The original planned data is **never mutated**.

```js
trip.review = {
  version: 1,
  status: "not_started" | "in_progress" | "completed",
  startedAt: <epoch ms> | null,
  completedAt: <epoch ms> | null,
  notes: "",                    // overall trip notes
  rating: 0,                    // optional 1–5

  // Keyed by prebooking section → item id ("1", "2", … as assigned by normalizeData)
  prebooking: {
    flights:    { "<id>": { actualCost: number|null, done: bool, notes: "" } },
    trains:     { "<id>": { ... } },
    bus:        { "<id>": { ... } },
    rooms:      { "<id>": { ... } },
    activities: { "<id>": { ... } },
  },

  // Keyed by "dayIndex|planTitle|itemIndex" — position-based with label snapshot
  timeline: {
    "0|Main Plan|2": {
      label: "Boarding",              // snapshot for drift detection
      plannedCost: 0,                 // snapshot at review time
      actualCost: number | null,
      done: false,                    // did we do/visit it?
      skipped: false,                 // explicitly skipped (done=false on purpose)
      notes: ""
    },
    // additionalBudget entries use "0|Main Plan|add|0"
  }
}
```

### Keying & drift rules

- **Prebooking:** key by `id` (positional but stable in practice). Each entry stores a compact snapshot (e.g. `"BLR→SFO|3 July 2026"` for transport, `name` for rooms/activities); if the live item no longer matches its snapshot, show the entry as *stale* and let the user re-confirm or clear it.
- **Timeline:** key by `itemId` (stable ids stamped by Phase 0 P0-3) with `dayIndex|planTitle|itemIndex` as a human-readable fallback key only for pre-id trips. Only the **active plan** of each day is reviewable (same rule as `calculateTotalBudget`). Each entry stores `label` + `plannedCost` snapshots; if the live item's title no longer matches, flag as *stale* instead of silently misapplying.
- Missing entries = **not yet reviewed** (defaults: not done, actual cost unknown). Sparse storage — we never write full templates for all items.

### Migration

- Trips without `review` → treated as `status: "not_started"`; no write needed until the user starts reviewing (lazy creation keeps old trips byte-identical).
- `normalizeData` keeps passing `review` through untouched (top-level spread already does this); add a small `normalizeReview(review)` guard for shape safety on import.

## 5. ReviewView (the review experience)

Entry points:

1. **Top Review button** — in `ItineraryView`'s actions bar (next to Download/Edit/Close), visible when `isTripInPast(...) || trip.archived`. Toggles the Review tab / opens review mode.
2. **Review tab** — a top-level tab in `Tabs.jsx` (after Budget), only rendered for past/archived trips.
3. **Dashboard card button** — on archived/past `TripCard`s, a small "Review Trip" button that opens the trip directly into the review tab. Wiring note: the open-trip flow in `App.jsx` currently hardcodes `setActiveTab('day-0')` — extend it to accept an initial tab (e.g. `openTrip(trip, 'review')`).

UI structure (single scrollable view, no nested tabs):

```
┌────────────────────────────────────────────────────────┐
│  Trip Review — "Trip to Madikeri (Coorg)"              │
│  Progress: ████████░░  18 / 27 items   [Mark Complete] │
│  Overall: Planned ₹48,200 → Actual ₹51,350  (+₹3,150)  │
├────────────────────────────────────────────────────────┤
│  ✈️ Flights / 🚂 Trains / 🚌 Bus / 🏨 Rooms / 🎯 Acts   │
│     per item: [✓ done] [actual cost ₹____] [notes]     │
├────────────────────────────────────────────────────────┤
│  📅 Day 1 — Journey, Check-in, …                       │
│     ☑ 5:45 AM  Leave Home                    ₹0        │
│     ☑ 8:15 AM  Highway Breakfast             ₹240 / ₹300│
│     ☐ 1:00 PM  Check-in Treebo Doha King   [x] skipped │
│        ↳ reason (optional): hotel fully booked…        │
│     …                                        [notes]   │
├────────────────────────────────────────────────────────┤
│  Summary: 24 done · 3 skipped · 0 pending              │
└────────────────────────────────────────────────────────┘
```

Behaviour:

- **Prefill:** the actual-cost input shows the planned cost as a *placeholder* (greyed), so "same as planned" is one keystroke — but `actualCost` stays `null` until the user commits a value, keeping the Budget Actual column at "—".
- **Input UX:** actual-cost inputs use `inputMode="decimal"` (numeric keyboard on mobile); Enter commits, Escape reverts; empty input → `actualCost: null`.
- **Auto-status:** first edit sets `status: "in_progress"` + `startedAt`; "Mark Complete" sets `completed` + `completedAt`.
- **Done vs Skipped:** `done = false` items ask nothing (pending); a **"Skipped" checkbox** marks intent, plus an **optional free-text box** for the reason. No structured reason picker (decided — see §13).
- **Stale entries** render with a warning chip and "re-link to current item / clear" actions.
- **Progress definition:** an item counts as "reviewed" when it is `done` **or** `skipped`; progress = reviewed / total reviewable items (prebooking + active-plan timeline + additionalBudget). Drives the header bar and the dashboard badge.
- **Mark Complete:** allowed even with pending items, but shows a confirm first ("N items not reviewed — mark complete anyway?"). Reopening a completed review flips status back to `in_progress`.
- **Restart review:** a "Clear review" action (behind `ConfirmPopover`) resets `trip.review` to `emptyReview()` — useful when re-running a repeated trip.
- **Trip notes & rating:** `review.notes` / `review.rating` get a collapsible card at the bottom of ReviewView.
- Every change saves immediately through `handleUpdateTripReview` (IndexedDB write per change is fine — it's what the app already does elsewhere; debounce if needed).

## 7. Visibility rules

- **Decided:** review is editable **only after the trip's end date has passed** (§13). Review tab + Review button appear when: `trip.archived === true` **or** `isTripInPast(trip.startDate, days.length)` — these coincide in practice, since `loadRecentTrips()` auto-archives past trips on app load.
- Ongoing trips ("Day 3 of 7"): **no review UI** — no Review tab, no Review button in the actions bar; cards keep the ongoing badge. Review unlocks automatically once the end date passes.
- Future trips: no review UI anywhere (cards show countdown instead).

## 8. Persistence & Data Safety

- Review state is part of the trip object → saved via `saveTrip` in IndexedDB; **automatically included** in `handleExportBackup` backups and restored by `handleImportBackup` (`normalizeReview` sanitizes at the import boundary — shipped early in Phase 0 P0-6).
- Review input changes go through the debounced save hook (`useDebouncedSave`, Phase 0 P0-7): 300–500 ms debounce, flushed on tab switch / close / `beforeunload`.
- Deliberately **not** following the existing localStorage checklist pattern (fragile key, not backed up, lost on title change). New state goes through the trip object.
- `handleUpdateTripReview` writes to IndexedDB immediately — review edits bypass the `edits_made` unsaved-changes flow (planned-data editing stays as-is).
- **PWA (verified):** `vite.config.js` uses `vite-plugin-pwa` with `registerType: 'autoUpdate'` and the default generated service worker (no custom workbox config). IndexedDB access is unaffected by SW caching, so review data gets offline persistence for free — no SW changes needed.

## 9. Edge Cases

| Case | Handling |
|---|---|
| Review attempted mid-trip (end date not passed) | No UI is rendered (§7); `handleUpdateTripReview` additionally guards and ignores writes until the end date has passed |
| Trip edited after review started | Snapshot `label`/`plannedCost` mismatch → *stale* chip, user re-confirms |
| User switches a day's `active_plan` | Only active-plan items are reviewable; entries for other plans stay stored but hidden |
| Items with no planned cost | Still reviewable for `done` (visited); actual cost optional |
| `excludeFromBudget` activities | Reviewable (visited?) but excluded from all totals |
| Currency | Use existing `getCurrencySymbol(trip.currency)`; actuals assumed same currency (no FX in v1) |
| Legacy trips / old backups | No `review` key → everything defaults gracefully; `normalizeReview` sanitizes malformed shapes |
| Very long trips | ReviewView groups by day with collapsible sections (reuse the `ChevronDownIcon` accordion pattern from BudgetView) |
| Trip with nothing to review (no prebooking, no costed timeline items) | Empty state: "Nothing to review — add costs to your itinerary first" |

## 13. Decisions (resolved)

1. **When can a trip be reviewed?** Only **after the trip's end date** — no "mark as you go" during an ongoing trip. Drives the visibility rules in §7 and a write-guard in `handleUpdateTripReview` (§9).
2. **Skipped items:** a **checkbox** plus an **optional free-text box** for the reason. No structured reason picker in v1 (kept as a future idea in §12).
3. **Range cost strings** (e.g. `"₹600 – ₹1,000"`, present in real sample data): canonical `parseCost` takes the **first number** (₹600). Locked in Phase 0 P0-1, pinned by unit test.
4. **`updatedAt` reorder:** review edits bump `updatedAt` (via `saveTrip`), surfacing recently-reviewed trips on the dashboard — accepted behaviour.
5. **Existing localStorage checklist/prebook state:** migration into the trip object is **deferred** (tracked in `REVIEW_READINESS_PLAN.md` G5); the Review feature uses trip-object state only and never extends the localStorage pattern.
